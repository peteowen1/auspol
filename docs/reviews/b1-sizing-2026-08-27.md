# B1 sized before building: the multi-candidate case is real but tiny

2026-08-27. Before committing to B1 (seat × candidate matrix, replacing the
seat × party-class matrix everywhere), sized the problem it would fix — per
`CLAUDE.md`'s "size the effect before building the fix."

## The scare, and the correction

**27.5% of non-major seat-class rows (1,992 of 7,249) have 2+ simultaneous
candidates.** Several of today's marquee cases are among them — Kooyong,
Warringah, Mackellar, Wentworth. First reaction: this could invalidate
everything shipped today, since the model sums a class into one column and
cannot represent two independents in a seat separately.

**Checked immediately, and it doesn't.** In every multi-IND case inspected —
Kooyong, Warringah, Mackellar, Wentworth — salience's top-2-per-seat-plus-
every-IND fetch rule already queried every candidate and correctly identified
the actual winner. That validates the salience results independent of the
seat-model architecture question.

## Sizing the seat-model question itself

Of the 1,992 multi-candidate instances:

| second-placed candidate polls | count |
|---|--:|
| >10% (a genuine contest) | **8** |
| >5% | 57 |
| <1% (pure noise) | 474 |

**Only 8 of 1,992 are a real two-way split.** The other 1,984 are one strong
candidate plus one or more no-hopers, where summing the class barely moves the
total.

Of those 8, only **3 saw the class actually win the seat**: Kimberley 1996
(33.8/29.3), Alfred Cove 2001 (20.3/20.1), Calare 2025 (23.7/15.8). Three seats
across 24 elections.

## What this means for the plan

**B1 as scoped is not justified by this evidence.** The big win already
shipped — arm CS, candidate identity changing the slope on a class's swing —
does not need candidate-level columns; it only needs to know *whether* the same
person returns, which `candidate_returns()` already answers by matching within
(seat, class). The genuine multi-candidate-column case is real but affects
roughly 3 seats in the entire corpus.

A full seat × candidate rewrite would still need a redesigned flow matrix (raw
transfer files record `from`/`to` as party classes, not candidate names, so
candidate-level flows would need their own construction), a no-op proof, and
re-measurement across all five harnesses — the cost the plan already flagged as
"the largest ticket here." That cost is not worth 3 historical seats.

## What is still worth doing

- **B2 (compositional/softmax shares)** stands on its own evidence, unrelated
  to this sizing, and remains the better-targeted next structural change.
- **A cheap, scoped fix for the 8 genuine splits**, if wanted: detect a
  seat-class with a second candidate above some threshold (10%?) and flag it
  for manual review rather than silently summing, rather than building the
  full architecture to handle a case this rare automatically.
- **B1 stays on the plan as a longer-term item**, re-scoped: not "everything
  goes through candidate rows" but specifically for whatever the next
  measured problem turns out to need it.

## Status

B1 downgraded from "largest ticket, do it next" to "sized, and not currently
justified." B2 becomes the next structural priority.
