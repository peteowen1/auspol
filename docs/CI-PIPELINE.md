# auspol forecast pipeline

_Generated by `ops/scripts/pipeline_guide.py` from `docs/pipeline.json` on 25 Nov 2026, 11:59am (Sydney time). Do not edit by hand, except the notes section: rerun the generator._

What the daily Victorian (and NSW 2027) forecast run does on GitHub Actions, in order, and how long each part takes: from fetching the polls to the forecast and the what-if sliders landing on the release and the data store the site reads. The model's own stages (the forecast's four steps and the rebuild's eight) are described in docs/PIPELINE.md; this file is the GitHub Actions run that executes them every day.

## Daily forecast refresh

Workflow: [`forecast.yaml`](https://github.com/peteowen1/auspol/blob/HEAD/.github/workflows/forecast.yaml). Median wall time **35 min 12 s** (range 32 min 26 s to 45 min 24 s), from the first job starting to the last job ending, over the 5 run(s) listed below.

One run per day. The forecast job publishes first; then 16 what-if jobs (4 parties, 2 modes, 2 elections) rerun the seat model with one party's vote forced, side by side, and a last job combines and publishes them. Only full daily runs are counted: the title must say "(daily)" and the what-if jobs must have run. From 25 Nov 2026 every run uses 100,000 simulations (was 20,000), so runs before that date are faster than today's.

**What starts it, and what it starts:** The inthegame-blog site's worker dispatches it at 4:30am Melbourne time with daily=true; GitHub's own schedule (17:37 UTC) is a late fallback that the gate job skips when the day's run already went. It starts nothing else: the site reads the files it publishes.

5. **The what-if jobs themselves.** Each forced vote level genuinely reruns the seat model; more parallel jobs is the other lever, and Actions minutes are free on this public repository. Their R install steps sometimes crawl and retry (see the Ran column).

## How to regenerate

```
python C:/dev/ops/scripts/pipeline_guide.py build --repo-dir <this repo>
```

It reads `docs/pipeline.json` (which workflows and jobs are the pipeline, one line per step) and the latest successful runs through `gh`, saves every response raw, and rewrites this file and `docs/pipeline-summary.json`. It fails if the config names a job, step or log pattern that no longer appears, so a renamed step cannot leave a stale description behind. Steps marked **(not confirmed)** were not checked against the script they run.
